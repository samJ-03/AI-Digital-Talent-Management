# 当前代码架构与目录导航

更新：2026-11-09。以实际目录与代码为准。当前T01～T12完成，T13文本解析/字段提取与T14导入受理子任务已验证；最近完整回归280通过，下一步T15人才建档。后续招聘业务页面、字段提取和完整邀考仍未完成。

## 1. 先看懂两条轴线

本项目是**前后端分离的模块化单体，加独立后台工作进程**。

第一条轴线是业务领域：账号、岗位、解析、考试、模型、邮件各自一个包。第二条轴线是技术分层：每个领域内部通过router → service → model/适配器组织调用。因此不是把所有Controller、Service和Model集中到三个全局目录。之前总体设计中的application/domain/repository/adapters是目标逻辑职责，不是当前已经存在的文件夹。

传统MVC对应：Next.js页面是View，FastAPI router是Controller，SQLAlchemy models是持久化Model。额外拆出的service承接业务规则和事务；schemas承接请求/响应类型。后端views.py只是DTO投影，不是网页，也不等于SQL视图。

## 3. 用jobs模块看清实际分层

| 逻辑层 | 当前文件 | 主要职责 |
|---|---|---|
| HTTP控制器 | backend/app/jobs/router.py | 接收请求、身份依赖、If-Match/幂等键、调用服务、封装响应 |
| 输入输出契约 | backend/app/jobs/schemas.py | JobCreate、JobVersionDraft等；字段类型、权重及模板校验 |
| 应用服务/业务编排 | backend/app/jobs/service.py | JobService；部门权限、状态变化、发布快照、开启邀请、审计和事务 |
| 业务前置规则 | backend/app/jobs/readiness.py | 检查岗位、试卷、模型和邮件依赖，输出阻塞原因 |
| 持久化模型 | backend/app/jobs/models.py | Job/JobVersion映射、外键、索引和字段说明 |
| 响应投影 | backend/app/jobs/views.py | 将实体转换为允许返回的DTO，控制ID/时间等展示格式 |
| 通用事务与鉴权 | backend/app/core/uow.py、hr_service.py、access.py | 统一提交/回滚、身份与权限复验、幂等命令 |

当前没有单独的jobs/repository.py：SQLAlchemy查询仍在service或专门queries模块，不能声称已经做到严格Repository分层。当前也没有每层独立目录。后续若服务明显膨胀，再逐模块提取queries/repository及纯规则；不为目录外观一次性搬动全部业务代码。

## 4. 一次建岗请求怎么流转

~~~text
HR页面（岗位页面待实现）
  → frontend/src/lib/http.ts：发HTTP请求
  → jobs/router.py：POST /api/v1/jobs，解析JobCreate与身份
  → jobs/service.py：JobService.create，核对部门和岗位权限
  → core/hr_service.py + core/uow.py：幂等、业务写入、审计同事务
  → jobs/models.py + MySQL：保存Job，初始draft且自动邀请关闭
  → jobs/views.py：安全DTO
  → router.py：响应、ETag
  → 页面展示
~~~

这是对已有后端调用链的解释；岗位前端还未落地，不能把上面的目标页面当已完成。建岗不直接发信；开启自动邀请也只写invite.scan事件，消费与实际邀考留T22/T23。

## 5. 外部I/O与后台任务在哪

| 能力 | 实际文件/模块 | 说明 |
|---|---|---|
| MinIO文件 | files/storage.py | 私有对象读写；业务授权由FileService控制 |
| SMTP | notifications/smtp_adapter.py | 邮件连接和投递边界；本地Mailpit与企业SMTP分开 |
| 模型调用 | ai_runtime/gateway.py、ollama_adapter.py | 受控供应商调用、schema/证据校验；不允许模型直接操作业务 |
| 文档解析 | ingestion/parsers.py、parse_worker.py | 有资源预算的独立子进程；当前只支持文本PDF与受限DOCX |
| 消息与任务 | runtime/outbox.py、job_service.py、worker.py | MySQL保存任务事实，Redis/Celery负责交付 |
| 定时恢复 | runtime/scheduler.py | 自建单实例调度，不是Celery beat |

不要让router执行长时间解析；不要在持有数据库锁的事务里等待AI、OCR、SMTP或对象存储网络调用。事务边界由服务/UoW控制。

## 6. 推荐阅读顺序与当前不整齐的地方

先读本文件 → main.py看装配 → jobs/router.py看入口 → schemas.py看数据 → service.py看业务 → models.py看落库 → core/uow.py看事务 → 对应测试看失败场景。其他领域沿同样方法阅读。

当前属于领域分包＋逐步实施阶段，存在auth_service/config_service/question_service等按用途命名的服务，尚未统一拆成api/application/domain/infrastructure目录；assessment/models因表族较多先做了子包；verify_*/seed_*辅助入口尚有部分放在领域包中。这些是真实结构差异，文档应直说，不能用目标目录掩盖现状。

本轮仅补齐架构导航、模块入口和离线图；未移动Python模块、修改导入或改变业务行为。若后续要物理重构，以单个领域为单位保留HTTP契约并跑对应回归，避免大规模目录搬迁打断核心交付。
