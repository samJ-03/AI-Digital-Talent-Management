# 技术栈职责与选型对比详解

版本：V1.0｜2026-11-06｜配套[02-本机环境与技术选型](02-本机环境与技术选型.md)及[03-总体架构与技术设计](03-总体架构与技术设计.md)。

本文解释“这项技术具体干什么、为什么保留、为什么当前没有选择其他方案”。精确版本与实施状态以02为准；下面的替代方案判断是针对本项目需求、已有代码和部署条件的工程取舍，不是厂商排名，也不是未经测试的性能结论。

## 1. 先确定需要解决的问题

本项目面向单企业外部人才招聘。管理员配置账号/权限/模型；HR负责招聘；目标包含候选人独立考试入口（当前待实现）。部门负责人属于已提出的后期角色，当前代码未实现。需要承接的核心问题包括：

1. 简历原件、结构化履历、岗位标准、考试和评价必须各有归属与版本。
2. 共享人才画像只能含允许共享的事实，本部门考试/面试评价不能泄漏到其他部门的共享检索。
3. 解析、模型、向量和邮件会慢或失败，不能卡住用户请求或造成重复邀考。
4. 简历画像、岗位匹配和考试成绩是不同概念；AI只能辅助，不自动决定录用。
5. 答卷要可靠保存，不能因浏览器关闭、Redis过期或Worker重启丢失。
6. 第一阶段优先完成可追溯的业务闭环；不能仅因为本机装有某软件就把它设为依赖。

因此采用模块化单体API + 独立Worker/调度器。部署进程可以分离，领域代码及MySQL事务仍集中管理；当前不是一整套招聘微服务。

## 2. 技术总览：从页面到数据

| 层 | 当前采用 | 具体承接的工作 | 不承担的工作 |
|---|---|---|---|
| 页面与交互 | Next.js、React、TypeScript、Ant Design | 岗位表单、人才列表、画像详情、试卷编辑、考试答题的界面基础 | 不决定数据权限、正式分数或服务端截止时间 |
| 前端服务器状态 | TanStack Query | 加载/错误/重取、查询失效与页面刷新 | 不保存永久答卷，不替代数据库 |
| HTTP业务入口 | FastAPI、Pydantic、Uvicorn | 登录、CRUD、DTO验证、标准响应与OpenAPI | 不在长请求中等待整批OCR/模型执行 |
| 业务事实 | MySQL、SQLAlchemy、PyMySQL、Alembic | 版本、关系、状态、事务、审计、迁移 | 不用向量相似度替代关系约束 |
| 异步与短期状态 | Redis、Celery、应用scheduler | 会话/限流、任务交付、后台执行、租约恢复 | Redis/Celery不单独决定业务是否成功 |
| 文件 | MinIO、minio SDK | 存简历/资料原件，后端授权读取 | 不直接承担人才查询、岗位筛选或权限决策 |
| 语义索引 | Milvus、PyMilvus、Embedding模型 | 后续语义召回、岗位推荐、知识检索 | 不保存唯一事实，不把相似度当最终匹配成绩 |
| AI执行 | HTTPX模型网关、LangGraph、Pydantic/JSON Schema | 受控生成、验证、调用记录和固定子图 | 不运行模型生成的SQL，不授权任意业务写工具 |
| 文档处理 | 当前轻量依赖 + 待评测MinerU/PaddleOCR等适配器 | 从文件取得文字、结构、页/段来源，供后续提取 | 不直接完成身份合并、岗位判断或录用 |
| 开发与运行 | Docker Linux、Compose、Nginx、pytest、Git/GitHub | 隔离依赖、同域入口、验证和版本托管 | 不等于已具备生产高可用或已完成业务验收 |

有些行描述目标职责，而非全已实现；02的状态表明确区分，T12之后的业务仍按计划开发。

## 3. 前端：为什么是这一组

### 3.1 Next.js + React + TypeScript

具体作用：Next.js负责页面路由、构建与前端服务；React组织交互组件；TypeScript在开发时约束字段与接口类型。当前前端经Nginx调用同域/api/v1，招聘业务统一进入FastAPI。

| 可选方案 | 当前选择的原因 | 代价/何时会重新考虑 |
|---|---|---|
| Next.js vs Vite + React SPA | 已有Next.js16骨架、构建及部署验证，可沿用页面组织；保持一套既有前端路线 | 本系统后台并不需要SEO，Vite SPA也完全可行且可减少部分框架概念；如果从零只做内网SPA，它是合理候选 |
| React vs Vue3/Nuxt | 当前组件、Query和Ant Design已围绕React建立；替换将重写界面及测试，没有已确认业务收益 | Vue也能实现相同招聘功能；如果交付团队明确以Vue为主且愿意承担迁移，才值得再选 |
| TypeScript vs JavaScript | 岗位、版本、考试和DTO字段多，类型检查能提前暴露调用错误 | 类型不会在运行时自动验证外部数据，仍需后端Pydantic和错误处理 |

当前没有使用Next.js Server Actions另写招聘事务，也没有把SSR当作后台必须条件。

### 3.2 Ant Design、TanStack Query、ECharts

| 技术 | 具体作用 | 为什么选它，为什么不换其他 |
|---|---|---|
| Ant Design | 表格筛选、表单、弹窗、状态反馈及后台布局组件 | 符合当前后台表单/表格密集的界面，已有主题和组件接入。MUI、其他React组件库也能做；当前重选会增加样式和组件适配，缺少明确收益。Element Plus属于另一套Vue组件路线，不能直接代替现有React组件 |
| TanStack Query | 请求去重/缓存、加载错误状态、操作后失效重取 | 后台大量状态来自服务器，避免每页手写一套请求生命周期。现阶段无需为这些服务端数据再引入Redux全局镜像；表单局部状态用组件即可，复杂客户端状态以后按需求评估 |
| ECharts | 未来招聘漏斗、阶段趋势、成绩和待办统计的图表 | 作为既定图表依赖保留。Chart.js、Recharts也是可选；当前尚未实现统计页面，没有做图表性能优劣结论，不因装包就声称看板完成 |

## 4. API与数据访问：为什么采用Python/FastAPI

### 4.1 Python、FastAPI、Pydantic、Uvicorn

在本项目中：FastAPI接收请求并执行权限依赖；Pydantic验证输入/输出及业务结构；Uvicorn运行ASGI应用；Python同时承接解析、规则和AI适配。FastAPI不是OCR引擎，也不会自动让阻塞任务变快。

| 替代方向 | 当前不切换的理由 | 替代方案仍适合的情况 |
|---|---|---|
| Django + DRF | Django自带后台/认证有价值，但当前已有定制账号隔离、SQLAlchemy40表、幂等和审计；迁移会重做已验证部分 | 从零做以常规管理CRUD为主、团队熟悉Django的项目，可以优先考虑 |
| Flask | 可实现相同服务；目前Pydantic和OpenAPI契约已经贯穿代码，不再自行组合另一套入口规范 | 很小的定制API或团队已有成熟Flask规范时适用 |
| Spring Boot | 企业业务及权限体系同样可用；本项目AI/文档处理已在Python，改Java主服务会增加跨语言接口或重写成本 | 已有Java团队、企业治理/基础设施以Java为主时有优势 |
| NestJS/Node后端 | 能与前端统一语言，但目前会重写Python领域层，并重新处理文档/OCR适配的协作 | 从零、TypeScript团队占主导且能维护Python解析独立服务时可选 |

这不是“Python吞吐必然最高”的选择。CPU密集解析和OCR仍放入后台受控进程；需要通过T41实测性能与资源。

### 4.2 SQLAlchemy同步Session + PyMySQL + Alembic

- SQLAlchemy描述实体/关联/索引，并执行行锁、查询和事务；PyMySQL负责MySQL通信；Alembic记录可复现迁移。三者职责不同。
- UoW显式提交；业务行、审计、幂等结果、Outbox尽量在同一MySQL事务中落地。Repository或回调不能私自提交外层事务。
- 选择同步Session/驱动以减少当前实现复杂度；同步路由/Worker与它配套。不是在async函数里阻塞执行SQL、模型或OCR。
- async SQLAlchemy可在后续确有大量并发I/O需求且经过压测时评估；不能仅把def改成async def就称性能升级。
- 直接拼SQL虽然简单，但本项目有大量外键/版本/CAS/迁移核对，长期手工维护代价较高；关键SQL仍可显式执行，不把ORM当作必须隐藏所有SQL的黑盒。

[SQLAlchemy官方会话与事务说明](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)说明Session承接连接与事务生命周期；本项目的同步/异步取舍则基于现有代码与验证成本。

## 5. 四类存储：同一个候选人的数据分别去哪

| 数据例子 | 放哪里 | 原因 |
|---|---|---|
| 候选人A的身份、简历版本、岗位关系、人工破格记录、考试答案和正式成绩 | MySQL | 需要关联、事务、版本、权限和可追溯历史；部分业务待后续任务实现 |
| A上传的PDF、Word、扫描图片 | MinIO | 二进制原件独立管理，MySQL存file_id、对象键和元数据 |
| A的允许共享画像产生的检索向量 | Milvus | 供后续语义召回；必须能从MySQL版本与模型配置重建 |
| A当前邮箱核验的短期状态，HR后台会话，后台任务交付消息 | Redis | 适合有有效期的状态及任务消息；永久业务事实仍在MySQL |

部门负责人未来查看A时，由后端先验证A与本部门岗位的招聘关系。不能仅按MinIO桶名、Redis键或向量标签就认定有权限；新增负责人角色尚未实现。

### 5.1 MySQL，而不是现在迁到PostgreSQL/MongoDB/SQLite

当前实际固定MySQL8.4.13，已有40表、478字段、真实FK/唯一约束、行锁、乐观锁、迁移及一致性测试。它承担唯一业务事实来源。

| 方案 | 适合点 | 本项目当前取舍 |
|---|---|---|
| PostgreSQL | 关系数据库，同样能承接事务和复杂查询 | 不是能力不足而不选；当前迁移需复核MySQL方言、类型、索引/排序规则、锁和迁移。用户已选择“改动大则保留原栈”，因此不为换库而换库 |
| PostgreSQL + pgvector | 可以把关系数据与向量放到同一数据库体系，减少一种独立服务 | 如果从零开始且规模/负载适合，这是值得认真比较的更简单部署路线。当前沿用已验证MySQL与Milvus，不宣称双数据库天然比它更好。pgvector能力依据见[官方项目](https://github.com/pgvector/pgvector) |
| MongoDB | 文档型数据和灵活结构可用 | 本系统主要挑战是人才×岗位×版本×考次×成绩的关系与历史，当前用关系模型直接表达；灵活原始结构可放受类型约束的JSON字段，无需新增主库 |
| SQLite | 本地原型、离线演示或轻量工具可用 | 当前目标为多角色共享服务和并发保存/任务协调，已采用独立MySQL部署；不再为了减少一项服务改变已验证事务与部署路线 |

数据表存在不代表业务实现完成。例如jobs表已建，JobService的岗位发布和自动邀请配置仍待T12。

### 5.2 Milvus，而不是把向量当人才库全部

Milvus负责未来语义召回：找“与该岗位相关的候选人/经历/知识片段”，不是SQL查询、硬条件判断或正式分数存储。SDK为PyMilvus，Embedding来自百炼；这三个组件不能互相混称。

选择理由：当前已部署并做过合成向量插入/检索，向量索引与业务事实分开，便于按实体版本/模型配置重建。后续权限过滤检索必须先限制可检索集合，召回后再回MySQL复查当前版本、有效状态和权限。[Milvus官方过滤检索说明](https://milvus.io/docs/filtered-search.md)

代价是要维护Milvus及其依赖、索引同步与一致性。Qdrant也是独立向量数据库候选；pgvector可减少独立服务；Elasticsearch可在已有全文检索平台时一并评估。当前没有用同一批招聘数据压测这些方案，不能写成“Milvus一定更快、更准”。

结构化硬筛由业务规则执行；余弦相似度不能乘100直接作为岗位能力分。共享画像/向量不能混入部门私有考试、面试评价；这不是向量数据库自动替我们完成的规则。

### 5.3 MinIO，而不是将文件塞入数据库或项目目录

MinIO保存原件；minio SDK执行对象读写。业务桶talent-business和Milvus内部桶分离。当前下载方式是后端授权的附件代理流，不向浏览器直接暴露内部对象键或默认提供永久公开链接。

| 方案 | 当前取舍 |
|---|---|
| 本地磁盘路径 | 简单原型可用；本项目需要文件生命周期、授权代理及独立服务存储，避免API容器重建影响原件。使用MinIO并不代表备份自动完成，恢复验收仍在T42 |
| MySQL BLOB | 可以保存二进制，但本项目将文档原件与结构化事实分离，减少常规查询/备份与大文件传输耦合 |
| 云S3/其他S3兼容服务 | 可作为生产部署替代；当前选MinIO方便独立开发环境与接口验证，不意味着永远不能更换存储后端 |

MinIO自身的存储权限用于限制服务账号；候选人、岗位和部门的业务授权仍在应用服务层。

### 5.4 Redis，而不是用它保存全部状态

当前Redis已经用于会话、CSRF/限流相关状态和Celery交付。后续候选人验证码和可重建缓存可沿用。其TTL适合短期状态，但答卷、正式成绩和任务结果不能只存在Redis。[Redis官方用途](https://redis.io/docs/latest/develop/use-cases/)

替代选择：数据库也能实现会话和任务轮询，但会把短期高频访问叠到业务库；当前已有Redis/Celery组合，因此保留。需要单独缓存、队列系统或其他Redis兼容实现时，先验证客户端、持久化、命令和部署兼容，不靠名称相似认定可直接替换。

## 6. 后台任务：Celery、Outbox和scheduler各管什么

以未来“导入简历”举例：

~~~text
HTTP校验并提交导入记录 + background_job + outbox（MySQL同事务）
→ dispatcher投递数字任务ID到Redis
→ Celery Worker领取任务，MySQL租约确认执行权
→ 文件/OCR/模型等外部工作在长事务之外执行
→ 短事务核对状态/版本，提交阶段产物和下一步事件
~~~

任务框架已做，完整导入链路要在T13～T15等实现。

| 组件 | 确切责任 | 为什么需要 |
|---|---|---|
| Celery | 执行代码白名单处理器、使用后台进程承接耗时任务 | 不让HTTP连接等待整批解析/模型/邮件；不是唯一任务事实库 |
| Redis | 传递任务消息 | 和已有会话基础设施复用；消息可能重复，不能以“收到一次”假设恰好执行一次 |
| MySQL background_jobs | 持久任务头、输入/结果引用、状态、重试与租约 | 让重启后能核对任务是否执行、是否失去租约 |
| MySQL outbox_events | 与领域数据同事务写入待交付事件 | 避免业务提交成功但消息未投递；失败后可恢复派发 |
| 应用自建scheduler | 单实例扫描、过期租约恢复、事件再投递、短期载荷清理 | 当前由MySQL advisory lock限定单实例；没有运行Celery beat |

FastAPI BackgroundTasks、线程内起任务适合轻量非关键后处理；本项目不把它们当持久任务恢复机制。RQ/Dramatiq可以作为较轻的队列方案，但现有Celery/租约/Outbox已落地，切换需复核恢复与交付规则。

Redis broker目前足够承接已验证的基础任务；RabbitMQ在需要其特定路由和消息治理能力时可评估，Kafka适合不同的事件流需求，当前没有引入第二套消息服务的已确认收益。这里没有“所有规模都用Redis最好”的结论。

Worker放Linux容器，是因为Celery官方不支持原生Windows；Windows仍可作为开发宿主。[Celery官方平台边界](https://docs.celeryq.dev/en/stable/faq.html)

## 7. AI：模型、流程框架与业务决定分离

### 7.1 DeepSeek、Embedding、Rerank不是同一个任务

| 能力 | 当前选择及作用 | 为什么这样选 | 尚未做/不能替代 |
|---|---|---|---|
| 生成 | 官方deepseek-flash；按schema输出解释或结构化内容 | 用户明确选择，已有官方凭据和真实合成JSON证据；通过受控网关接入 | 不能从3组合成样本推出招聘评分已达标；GPT/Claude/其他通义模型等可作为未来同样本对比对象，当前无对比评测，不以未核实价格/排名作为理由 |
| Embedding | 百炼text-embedding-v3；把允许检索的文本转为1024维向量 | 用户指定，真实合成鉴权和维度已验证 | 向量不是能力分，实际人才召回待T20；本地bge-m3也可评估，但目前没有该路线完整质量证据 |
| Rerank | qwen3-rerank可选，对召回候选重新排序 | 留作T20评估，先看是否带来可测收益 | 当前没有真实效果验收；不能默认增加每次查询的成本与延迟 |
| 本地模型协议 | Ollama受限适配 | 为本地部署提供替换点、核验真实digest | 发现模型文件不等于可用；硬件、延迟、提取质量和运维需单独测，不再把本地小模型当当前默认主模型 |

网关、发布提示词、配置修订和输出类型让模型切换尽量局部化；切换Embedding仍需重建兼容索引，不能把不同配置/维度的向量混用。云端不提供权重digest时保留NULL，不伪造“已锁死供应商权重”的证明。

### 7.2 HTTPX + Pydantic + JSON Schema为什么同时存在

HTTPX承接受限地址、认证、超时、重定向拒绝与响应大小处理。Pydantic验证业务类型；发布的JSON Schema冻结该提示词版本的输出结构；额外逻辑检查来源ID和引文是否真实存在于允许输入。

仅用正则或json.loads只能证明能否解析，不足以约束引用与字段。使用供应商JSON模式能改善格式，但不能替代应用校验；官方也描述了截断或空内容等处理边界。[DeepSeek JSON输出说明](https://api-docs.deepseek.com/guides/json_mode/)

当前主业务调用直接使用HTTPX，而不是把OpenAI SDK、LangChain通用链或浏览器插件当成不可替代依赖。SDK方案也可用；这里保留较薄适配层，便于测试供应商失败、拒绝代理和控制返回内容。

### 7.3 为什么保留LangGraph，但不做通用Agent/Dify平台

已实现的固定图只接受代码注册的任务及输出类型，核心是invoke_and_validate。当前简单场景用普通Python函数也能实现，LangGraph的收益是保留统一子图组织方式，供后续检索/生成/验证扩展；它不是“装上就更聪明”。

没有配置持久checkpointer，不能声称LangGraph自身负责全项目断点恢复；跨任务恢复由MySQL任务、阶段产物、幂等和租约承担。LangGraph持久化能力需具体checkpointer配置，见[官方说明](https://docs.langchain.com/oss/python/langgraph/persistence)。

Dify适合可视化搭建一些AI应用，但本项目的考次、成绩确认、部门权限、Outbox与SMTP未知结果仍要由领域服务控制。当前再引入可视化执行平台会新增一套流程配置/状态协作，没有确认的收益，因此不作为一期依赖；未来确有非技术人员编排需求时可评估。

模型没有发送邮件、修改正式分数、决定录用的工具。是否破格、是否面试、是否录用仍由明确的业务权限与人工记录决定；近期新增规则尚待相应增量设计和实现。

## 8. 解析清洗：如何比较MinerU及原方案

“把文件读出来”“提取简历字段”“生成画像”“匹配岗位”是四个阶段，不应全叫OCR。

~~~text
MinIO原件 → 文档解析/版式/OCR → 带来源文字块
→ 清洗规范化 → LLM结构化提取 → 类型/证据校验
→ 简历版本 → 后续画像、硬筛与岗位匹配
~~~

| 方案 | 在本项目中的适用位置 | 取舍与现状 |
|---|---|---|
| pypdf | 文本PDF读取、当前PDF入口校验 | 轻量路径便于直接使用文本层，但不能靠它识别图片中的文字，也要测阅读顺序；完整解析器待T13 |
| python-docx | Word正文/表格读取 | 已锁依赖，适合受支持的DOCX路径；不能把它写成旧DOC的通用解析器 |
| PaddleOCR | 图片/扫描件文字识别的原设计候选 | OCR识别结果还需要页面结构、来源映射和清洗，版本及权重未冻结 |
| MinerU | 优先评测复杂版式、表格、双栏、扫描件到结构化内容的路径 | 官方提供文档解析和结构化输出，但本项目尚未安装/验证；不直接承诺它一定更准、更快或完全替代其他组件。[官方项目](https://github.com/opendatalab/MinerU) |
| LibreOffice | 必要时隔离转换旧DOC | 原方案方向，需测超时/字体/临时文件和页数；若原生解析路径通过再决定是否简化 |
| Docling/Marker/云解析API | 其他可比较的文档解析方向 | 当前未接入，也没有同样本实测；不能仅按通用宣传或排行榜决定招聘数据效果 |

T13选择主解析方案时，至少比较：普通中文/英文文本PDF、双栏PDF、含表格DOCX、扫描PDF、手机图片及旧DOC代表样本。逐项核对姓名/邮箱/教育/任职公司与时间/技能是否准确，是否串栏或漏段，能否定位来源，失败是否明确，并记录耗时和峰值内存。扫描PDF可能是逐页混合文本与图像，路由不能只按文件后缀一刀切。

当前确认的是“可替换适配器 + 原文/来源保留 + 明确失败”。没有最终确认MinerU与PaddleOCR的主次，也不默认让每份文件重复跑两套重型模型。具体模型权重、CPU/GPU路线、依赖和版本需评测后锁定并更新相应T13/OpenSpec增量；本说明不擅自修改已确认任务验收条件。

清洗优先使用可复现的Python规则：统一空白/编码形式，保留段落；日期/邮箱规范化保留原始值；低置信、缺失、冲突进入待核实。当前不需要为了称“数据清洗”就再引入Spark/Airflow等平台。大模型负责语义字段提取，不能负责猜造缺失身份信息；去重合并是独立业务规则与人工操作。

## 9. 身份安全为什么采用服务端会话和应用授权

当前后台登录使用Argon2密码哈希、Redis会话、auth_version失效控制、HttpOnly Cookie、写请求来源及CSRF验证。数据库通过RBAC权限码与部门/企业数据范围提供授权依据，服务端再从真实资源归属复验；没有引入Casbin、Keycloak或一套外部IAM服务。

| 替代做法 | 当前取舍 |
|---|---|
| 只用前端菜单隐藏 | 无法阻止直接调用API，不能作为权限方案 |
| 只把JWT放浏览器并相信其中的角色 | JWT也可以设计成安全方案，但本项目强调禁用/改角色后及时撤销，已使用服务端会话和认证版本；不再增加另一套撤销状态 |
| Keycloak/企业SSO | 组织统一认证需要时可接入；当前不增加独立IAM运维。接入后仍保留本项目资源级部门权限 |

Argon2哈希用于不能反解的登录密码；Fernet用于后端必须取出调用供应商的API/SMTP秘密。不能用可逆密码替代登录哈希，也不能把API Key只哈希后指望还原发送。主密钥必须独立保留，不与密文一起当作公开配置提交。

未来部门负责人角色要增加明确权限、部门范围和服务层路径；不能直接赋予管理员或全部HR权限来假装完成角色实现。候选人考试会话与后台账号域仍分离。

## 10. 部署、邮件和验证为什么这样选

| 组合 | 作用 | 替代方案及当前不选择理由 |
|---|---|---|
| Docker Linux + Compose | 固定镜像/依赖、隔离项目数据卷和端口、运行Worker/OCR等 | 直接装宿主也可，但更易与其他项目环境耦合；Kubernetes在多节点编排/组织已有平台时可用，当前单企业开发验证未需要这套运维复杂度 |
| Nginx同域反代 | /给前端，/api/v1给API，统一Cookie与入口；配置Docker DNS处理服务重建 | Caddy/Traefik可替换；当前已有Nginx配置与验证，不为反代名称重做。HTTPS是生产待完成项，不把本地HTTP说成已安全上线 |
| SMTP Adapter + Mailpit | 真实SMTP协议与本地收件箱，测试明确失败/接受/未知 | 企业SMTP或邮件服务API在正式接入时选择；当前不能以Mailpit收件成功声称外部候选人已收到邮件 |
| pytest + HTTPX | 确定性规则、权限、事务、迁移、受控供应商失败和真实本地依赖集成 | 单靠浏览器点通或只mock所有存储不足以证明一致性；真实付费模型检查单独运行，避免每次测试消耗额度 |
| Playwright | 后续完整页面和考试E2E | 与pytest分工；依赖存在不等于已做全链路浏览器验收 |
| Git + GitHub Actions | 提交历史、锁文件、CI流程 | 与Obsidian/OpenSpec各有职责；配置了CI不能直接宣称远端检查已通过 |

SMTP结果未知时可能已经发出，不能依靠无限重试实现“恰好一次”。MySQL唯一约束/幂等负责避免重复建考次；发送前二次验证和未知终态负责控制外部副作用。当前本地测试邮件已验证，真实邀考业务待T22/T23。

## 11. MCP、OpenSpec及明确暂不采用的技术

| 技术 | 正确定位 | 本项目当前决定 |
|---|---|---|
| MCP | AI应用连接工具、资源等能力的协议；不是数据库、缓存或OCR引擎。[官方架构](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/learn/architecture.mdx) | 当前没有业务集成。后续接企业日历/知识库等外部服务时，先定义工具权限、操作者与部门范围；模型不能借共享服务账号绕过权限 |
| OpenSpec | 管理增量规格/提案/任务的开发工具 | 本地已配置，不是生产依赖，不执行招聘，不替代Git或业务测试；本轮保留他人未提交的相关配置 |
| Neo4j | 图关系查询的一种方案 | 当前主线关系用MySQL可表达，无已确认图谱/多跳分析需求；不为“人才图谱”名称强加独立图数据库 |
| Vanna/NL2SQL | 自然语言查询数据库的工具方向 | 当前系统采用受限查询服务和参数化接口，不让模型自由拼SQL读敏感业务表 |
| Elasticsearch | 全文/搜索平台方向 | 当前已有结构化筛选与规划中的向量检索；只有确认全文相关性、运维和功能收益后再加 |
| 微服务/Kafka/Kubernetes | 更复杂的服务拆分、事件流或集群治理 | 当前没有作为主线完成的前置条件；规模、团队和压测证据出现后再作增量决策 |

## 12. 哪些情况下值得重新选型

| 触发条件 | 允许重新评估的方向 | 必须提供的证据 |
|---|---|---|
| 从零交付新版本，或多服务维护成本明显高 | PostgreSQL + pgvector等简化存储路线 | 迁移成本、真实检索及事务并发测试；不能删除既有历史来省事 |
| 简历双栏/表格/扫描识别不能满足质量门 | MinerU、PaddleOCR及其他解析器 | 同一批代表样本的字段、来源、失败率、耗时/资源对比 |
| 云模型提取/评分不满足业务质量或部署约束 | 其他云模型/本地模型 | 相同输入/schema/证据任务、失败处理、成本与延迟的实测 |
| 实际权限/治理需要企业统一登录 | SSO/IAM集成 | 明确角色映射、部门边界、注销/撤销及历史授权测试 |
| 实测并发/消息交付或运维成为瓶颈 | async I/O、其他broker、拆分服务等 | T41压测、故障恢复数据和迁移方案；不能先承诺2000人并发 |
| 确有外部工具交互需求 | MCP适配或普通API集成 | 明确外部系统、操作权限、用户确认和失败补偿；不是“有MCP就更好” |

技术选型的目标是把明确的招聘流程做对、可验证和可维护。现有选择都有代价，替代方案也有合理场景；本项目的理由是业务边界、已投入的实现/测试和当前部署条件共同决定，而不是列一串热门工具。
